# ADR 0004 — Optional installation of the options-backtest server

Status: accepted, 2026-09-27 (the owner request of 2026-09-27 is binding and recorded in §0; §15's defaults apply until the owner answers). Scope: how the `options-backtest-server` compose service and the `options_strategy_analysis` hub route that ADR 0003 added become an opt-in component across every lifecycle path — `install.sh`, `setup.sh`, `teardown.sh`, `obai start|stop|restart|teardown|upgrade|status`, the hub's enable flag and the paid E2E gate. Line numbers are as of HEAD `115d75e` on `feat/options-backtest-wp1`. Nothing here changes the server's behaviour, its tools or the specialist's contract.

## Decision

One persisted opt-in, `ENABLE_OPTIONS_STRATEGY=true` in `~/.obai/.env`, written only by `setup.sh` when it is run with `--with-options-backtest` (or flipped back with `--without-options-backtest`), drives everything: the compose profile `options-backtest` that the service is placed behind, the hub's `enable_options_strategy` (whose shipped default becomes `False`), the `obai status` entry, the `setup.sh` health check and summary line, and the four `CORE-OPTSTRAT-*` gate cases, which declare `requires: [options_backtest]` and are recorded as `skipped_not_applicable` — never run, never counted as passed — when the opt-in is off. A default install, start, upgrade or status touches nothing about the server: no image is pulled or built, no container starts, no health probe runs, the hub has no `options_strategy_analysis` tool and reports nothing degraded. `teardown.sh` always tears the service down whatever the opt-in says, and an opted-out `setup.sh` (with `--skip-mcp` or not) removes by name a container left by an earlier opt-in, found by a read-only query, because Compose's `down` and `--remove-orphans` both ignore a container whose profile is inactive. The flags are forwarded, not reimplemented: `install.sh` (`curl … | bash -s -- --with-options-backtest`), `obai start` and `obai restart` pass them to `setup.sh`, and a flag makes `obai start` a restart so a running web UI applies it; `obai upgrade` takes none and applies the persisted choice. There is no interactive prompt and no new `obai config` writer; `obai config show` gains a read-only "OBaI Optional Components" section with one row so the state is visible without Docker.

## 0. Owner request and the two-state contract

Owner request (2026-09-27, binding): "since it's a new server, let's not make it default while installing. Make it optional: only when it's opted in, install and enable it — including the main install script, upgrade and setup scripts. Also look into teardown, restart etc."

Read as a contract, every surface has exactly two states and one switch:

| Surface | Opted out (default) | Opted in (`ENABLE_OPTIONS_STRATEGY=true` in `~/.obai/.env`) |
|---|---|---|
| `docker compose … pull/build/up` (setup.sh) | service excluded by profile; nothing pulled, built or started; any leftover container removed | `--profile options-backtest`; image pulled or built, container started |
| `setup.sh` health list / summary | no `options-backtest:8012` probe; summary prints one hint line naming the opt-in flag | `options-backtest:8012` probed like its siblings; summary lists `options-backtest http://localhost:8012/mcp` |
| `teardown.sh`, `obai stop`, `obai teardown` | `down --profile options-backtest`: stops and removes everything, including a container from an earlier opt-in | same |
| `obai start` / `obai restart` / `obai upgrade` | run setup.sh; the persisted value applies; a flag on `start`/`restart` changes and persists it, after a teardown so a running web UI is relaunched | same |
| Hub (`enable_options_strategy`) | `False`: agent never constructed, no tool, not degraded (ADR 0003 §2.7) | `True`: agent built; a down server degrades `options_strategy` as today |
| `obai status` | no "Options Backtest" row; exit code unaffected by the server | row present; down server ⇒ exit 3 |
| `obai config show` | `options backtest  disabled  (from default)` | `options backtest  enabled  (from ~/.obai/.env)` |
| Paid gate (`CORE-OPTSTRAT-*`) | recorded `skipped_not_applicable` with the reason, no paid call, stderr warning, listed in `results.json` `skipped` | run and judged as today; preflight fails if the server is down |
| Hub prompt when the tool is absent | skill says backtesting is unavailable: the optional component is not enabled in this installation, or its server is not running | same sentence (a down server also removes the tool) |

Two properties follow and are what the tests in §10 pin: **(P1)** with no `ENABLE_OPTIONS_STRATEGY` line in `~/.obai/.env`, no path invokes anything named `options-backtest` except teardown's profile flag (which is idempotent on an absent container) and setup.sh's read-only `docker ps` query for a container left by an earlier opt-in, which it removes by name only when the query finds one; **(P2)** after `--without-options-backtest`, with `--skip-mcp` or not, `docker compose -p obai ps` shows no `obai-options-backtest-server`, `obai status` omits it, and a new hub has no `options_strategy_analysis` tool. A web UI that was running is relaunched without the route when the flag came through `obai start` or `obai restart`; one running before a flag given to `setup.sh` or `install.sh` directly keeps its route until `obai restart`, and the summary says so.

## 1. The single persisted opt-in

**Key, values, file.** `ENABLE_OPTIONS_STRATEGY`, exactly `true` or `false` (lowercase), one line in `$OBAI_HOME/.env` (`~/.obai/.env` by default; `install.sh:73` and `setup.sh:41` honour `OBAI_HOME`). Absent means `false`. This is the hub's existing field (`config.py:367`, env alias by pydantic-settings' case-insensitive matching), not a second infra key: every reader of the opt-in already reads that file — `setup.sh:102` and `install.sh:248,331` via their `load_env_file`, `chat.py:1147` via `_load_env_file` before any command, the gate via `effective_cli_environment` (`preflight.py:42-64`) — and deriving a hub flag from a separate `COMPOSE_PROFILES`-style key would add a second value that can disagree with the first. `settings.json` is rejected as the home: `HubSettings` is `extra="forbid"` (`hub_settings.py:74`), bash cannot read it without Python, and its contract is "hub settings are user-owned; specialists are code-owned" (`src/obai/CLAUDE.md`); an install-time component switch is neither.

**Writer.** `setup.sh` only, through a `save_env_key NAME VALUE` function extracted from the update-or-append block that `prompt_key` already contains (`setup.sh:166-181`; `prompt_key` calls it, so the file-writing code exists once in the script). It writes only when a flag was given; a run without a flag never touches the line, so a default install leaves no trace of the component in the file (P1). It finds a key's line the way the most lenient reader does — after `load_env_file`'s normalisation (UTF-8 BOM, CR, leading space) and allowing space before `=`, as the CLI does — rewrites the first such line and drops the rest, so the recovery flags always leave one canonical line. `install.sh` keeps `save_key` (`:250-266`) for API keys and does not write the opt-in: it forwards the flag to `setup.sh` (§4). No Python writer: `obai config set-key` is scoped to API keys by `_KNOWN_KEYS` (`chat.py:846-853`, masked by `show`), and a second writer with its own parser is a second place for the two sides to drift.

**Readers and their parsing.**

| Reader | Where | Accepts | On anything else |
|---|---|---|---|
| `setup.sh` | after `load_env_file` at `:102` | `true`, `false`, unset (⇒ `false`), from at most one line in the `KEY=` form | exits 1 before step 1 with the file path, the offending value (or "exported in your shell" when the file has no line for it) and the two flags that reset it; an empty value (`ENABLE_OPTIONS_STRATEGY=`) is "anything else" because `AgentConfig()` raises on it and every `obai` command, including `status`, would die. Two lines assigning the key, or one with space before `=`, exit 1 the same way: `setup.sh` takes the last line and needs `KEY=`, the CLI and the gate take the first and accept spaces, so either shape would split them |
| Hub, `obai status`, `obai config show` | `AgentConfig.enable_options_strategy` | pydantic's bool spellings | pydantic `ValidationError` (unchanged) |
| Gate runner (`run_suite.py`) | `effective_regression_environment()` | `true` ⇒ enabled; `false` or unset ⇒ disabled | `PlanError` ⇒ exit 2 naming the variable and the file, before any paid call |

The writer emits only the canonical spellings, so the readers agree whenever the file was written by the tool. A hand-edited `yes` or `1` fails loudly in `setup.sh` and the gate, and is honoured by the hub only until the next `obai start` names it; a hand edit that would make the readers pick different lines fails loudly in `setup.sh`. `teardown.sh` and Docker Compose read nothing: teardown does not need the value (§5) and Compose never reads `~/.obai/.env` (it reads the project-dir `.env`, `REPO_ROOT/.env`, which is gitignored and absent) — the profile reaches it as a CLI flag from `setup.sh` (§3).

**Precedence.** The file is authoritative for infrastructure. A shell export of `ENABLE_OPTIONS_STRATEGY` is unsupported and documented as such: `setup.sh`'s loader exports the file over the shell (the comment at `:100` says the opposite; the code at `:95` is what runs) while `chat.py:1141` and `preflight.py:62` let the shell win, so an export that differs from the file would start containers per the file and route per the shell. This ADR does not change either loader (both behaviours are shared by every key in the file and predate this work); it makes the disagreement visible where the user looks — `obai config show` warns when the environment holds the key and differs from the file, mirroring the hub-settings precedent (`_env_override`, `chat.py:914`) — and binds the variable into the gate's runtime fingerprint (§8) so an export cannot change routing without changing the run manifest.

**Same-run consistency.** `setup.sh` starts the web UI at `:570` with its own exported environment, which `load_env_file` filled at `:102` — before a flag on this run has been persisted. The resolution step therefore also `export`s the resolved value, so a hub started by this run sees the choice this run made. `setup.sh` never relaunches a web UI that is already running, and that UI's hub keeps its route for its whole life, so a flag on `obai start` runs teardown first, as `obai restart` does (§6). Clients already running when a flag is given to `setup.sh` or `install.sh` directly, or when a run removes a leftover container, keep their value until relaunch; the summary says so and names `obai restart`.

## 2. Compose profile

`docker-compose.yml:341-369` gains `profiles: ["options-backtest"]` under `options-backtest-server`. Nothing depends on the service and it depends on nothing, so no other service's activation changes. Facts verified on Compose v5.0.1 (`config` on a scratch copy of the file with the profile added; `rm --stop --force options-backtest-server` and `down --profile options-backtest` on an empty throwaway project name, both exit 0 and leave no container or network; `up`/`stop`/`pull` by the map's dry runs on a throwaway project name):

- Without the profile, `config --services` lists the ten default services; `pull`, `build`, `up` never touch the service or its image. With `--profile options-backtest`, `COMPOSE_PROFILES=options-backtest`, or `--profile '*'`, it is included.
- Naming the service on the command line (`up`, `stop`, `rm --stop --force options-backtest-server`) activates its profile without `--profile`; `rm`/`stop` exit 0 when no such container exists.
- `down` without the profile walks only the profile-filtered project, so a running `obai-options-backtest-server` from an earlier opt-in survives, keeps `obai-mcp-network` in use, and with `restart: unless-stopped` survives reboots. `--remove-orphans` does not remove it either: Compose treats a disabled-profile service as known, not orphaned.

Hence two rules: **teardown always passes the profile** (`--profile options-backtest`, the portable spelling; `'*'` is newer and catches only hypothetical future profiles), and **an opted-out `setup.sh` removes the container by name after `up`**. `--remove-orphans` stays on `up` for the purpose it already serves (services deleted from the file). The `version: '3.8'` obsolete-attribute warning is pre-existing and untouched.

## 3. `setup.sh`

**Flags** (`:53-68`): `--with-options-backtest` sets `OPTIONS_BACKTEST_FLAG=true`, `--without-options-backtest` sets it `false`; both on one command line exits 1 ("choose one"). Existing flags are unchanged. The `--help` window `head -22 "$0" | tail -16` (`:60`) is replaced by `sed -n '/^# Usage:/,/^# Prerequisites:/p' "$0" | sed '$d;s/^# \{0,1\}//'` so a longer usage block cannot silently truncate the help; a root test asserts that `--help` mentions every `--flag` label in the `case` statement.

**Resolution**, immediately after `load_env_file "$OBAI_ENV_FILE"` (`:102`) and before step 1, in one function:

```bash
resolve_options_backtest() {            # sets OPTIONS_BACKTEST=true|false; exports ENABLE_OPTIONS_STRATEGY
    if [ -n "$OPTIONS_BACKTEST_FLAG" ]; then
        OPTIONS_BACKTEST="$OPTIONS_BACKTEST_FLAG"
        save_env_key ENABLE_OPTIONS_STRATEGY "$OPTIONS_BACKTEST"
    elif ! opt_in_lines_read_alike; then                        # >1 line, or space before `=`
        fail "$OBAI_ENV_FILE must set ENABLE_OPTIONS_STRATEGY on one line, as ...=true or ...=false."
        info "Re-run with --with-options-backtest or --without-options-backtest to reset it."
        exit 1
    elif [ -z "${ENABLE_OPTIONS_STRATEGY+x}" ]; then
        OPTIONS_BACKTEST=false                                   # unset: default off, file untouched
    elif [ "$ENABLE_OPTIONS_STRATEGY" = true ] || [ "$ENABLE_OPTIONS_STRATEGY" = false ]; then
        OPTIONS_BACKTEST="$ENABLE_OPTIONS_STRATEGY"
    else                                                         # source: the file, or the shell when it has no line
        fail "ENABLE_OPTIONS_STRATEGY='${ENABLE_OPTIONS_STRATEGY}' $(opt_in_source) is not 'true' or 'false'."
        info "Re-run with --with-options-backtest or --without-options-backtest to reset it."
        exit 1
    fi
    export ENABLE_OPTIONS_STRATEGY="$OPTIONS_BACKTEST"
}
```

`save_env_key` does `mkdir -p "$OBAI_DIR"`, the update-or-append, and `chmod 600` (step 3's `mkdir` at `:332` runs later). `${VAR+x}` distinguishes unset from empty, so an empty line is rejected as §1 requires.

**Step 5** (`:422-497`). One argument array replaces the three literal invocations:

```bash
COMPOSE=(docker compose -p obai -f "$REPO_ROOT/docker-compose.yml")
[ "$OPTIONS_BACKTEST" = true ] && COMPOSE+=(--profile options-backtest)
"${COMPOSE[@]}" build            # :427 / :435
"${COMPOSE[@]}" pull 2>/dev/null # :430
"${COMPOSE[@]}" up -d --remove-orphans
```

**Leftover removal**, after step 5 whether or not `--skip-mcp` skipped it (opting out must leave nothing running, and `--skip-mcp` would otherwise keep a container that `restart: unless-stopped` brings back after a reboot):

```bash
OPTIONS_BACKTEST_REMOVED=false
if [ "$OPTIONS_BACKTEST" = false ]; then
    # Invisible to `down` and to --remove-orphans while its profile is inactive (§2).
    leftover="$(docker ps -aq --filter label=com.docker.compose.project=obai \
        --filter label=com.docker.compose.service=options-backtest-server)"
    if [ -n "$leftover" ]; then
        docker compose -p obai -f "$REPO_ROOT/docker-compose.yml" rm --stop --force options-backtest-server
        OPTIONS_BACKTEST_REMOVED=true
    fi
fi
```

The read-only query comes first so a default run with nothing to remove changes nothing and cannot be aborted by a removal it did not need, and so the summary knows whether a container a running web UI may still route to was just removed. Neither call is silenced and neither is `|| true`: a real failure to query, or to remove a container the user asked to have removed, must abort the run rather than be reported as success. The stale "Building 9 MCP server images" text at `:434` becomes count-free ("Building MCP server images") because the line is being edited anyway; no other message changes. The health array (`:455-466`) drops the literal `"options-backtest:8012"` and appends it under `[ "$OPTIONS_BACKTEST" = true ]`; the loop is unchanged. The summary (`:654-667`) prints `options-backtest http://localhost:8012/mcp` when opted in and otherwise one line: `Options backtesting (optional) is off — enable with: obai start --with-options-backtest`. When the run changed the saved choice or removed a leftover container, it adds that running sessions keep the old setting until `obai restart` and, when off, how to reclaim the image. The pre-existing omission of `crypto:8010` from both lists is left as ADR 0003 §7 left it.

**Behaviour in both states.** Opted out: no image of the service is pulled or built (profile), no container starts, the name-scoped `rm` clears a leftover when the query finds one, no probe hits `:8012`, the web UI starts with `ENABLE_OPTIONS_STRATEGY=false` exported. Opted in: `pull` includes the image; the existing all-or-nothing fallback (`:430-436`, any single pull failure builds every image locally) now also triggers when the registry lacks this image — a pre-existing shape, a §12 risk, not changed here; `up` starts it; `/health/ready` is probed; the web UI starts with `true` exported.

## 4. `install.sh`

`install.sh` has no flag parsing (`:72-77` read only environment). It gains a minimal loop before the banner: `--with-options-backtest` and `--without-options-backtest` are appended to `SETUP_ARGS`; anything else prints the two accepted flags and exits 1. The single call site `OBAI_MANAGED=1 ./setup.sh` (`:335`) becomes `OBAI_MANAGED=1 ./setup.sh ${SETUP_ARGS[@]+"${SETUP_ARGS[@]}"}` — the `${arr[@]+…}` form because the script runs under `set -u` and macOS ships bash 3.2, where an empty array expansion is an unbound-variable error. The header (`:8-17`) documents `curl -fsSL … | bash -s -- --with-options-backtest`, which delivers arguments through the pipe without touching stdin; a `read` prompt is not added because the piped script is what stdin is carrying (`README.md:97-101`). Semantics inherit from §3: a re-run without the flag keeps the persisted choice; opting out is `bash -s -- --without-options-backtest` or, after install, `obai start --without-options-backtest`. The post-setup banner gains one line naming the opt-in flag when the run was opted out.

## 5. `teardown.sh`

`:47` becomes `docker compose --profile options-backtest -p obai -f "$REPO_ROOT/docker-compose.yml" down 2>/dev/null`. Teardown reads no opt-in because it needs none: its job is "nothing left running", and the profile flag makes `down` see the service in both states at zero cost when the container is absent. Reading `~/.obai/.env` here would make `./teardown.sh` and `obai stop` (which inherits the CLI's loaded environment) diverge again. The `2>/dev/null` and the fail-soft branch are pre-existing and untouched. Data-volume and image semantics are unchanged: `obai stop` still preserves images.

## 6. CLI (`src/obai/clients/cli`)

**`lifecycle.py`.** `_run_script(repo_root, script, *args)` appends `args` to `["bash", script_path]` (`:74`). A pure `_setup_args(options_backtest: bool | None) -> list[str]` returns `[]`, `["--with-options-backtest"]` or `["--without-options-backtest"]`. `run_start(*, options_backtest: bool | None = None)` and `run_restart(*, options_backtest: bool | None = None)` pass them to the setup step; `run_restart` still runs teardown first with no arguments. `run_start` with a flag delegates to `run_restart`: `setup.sh` never relaunches a web UI that is already running, so without the teardown a running UI's hub would keep the old route, pointing at a container the opted-out run just removed. Without a flag `run_start` runs `setup.sh` alone, as before. `run_stop`, `run_upgrade` and `_apply_upgrade` (`:341-354`) are unchanged: an upgrade re-runs the *new* checkout's `setup.sh` with no flags, so the persisted choice applies, pulls happen only for enabled services, and — for a checkout that ran the pre-profile compose file with the default-on hub — the new `setup.sh`'s opted-out `rm` is what clears the container the old code started. `_confirm_upgrade`'s text (`:361`) is unchanged; "re-pulls Docker images" is true of the enabled set.

**`chat.py`.** `start` (`:782-788`) and `restart` (`:806-811`) gain `options_backtest: bool | None = typer.Option(None, "--with-options-backtest/--without-options-backtest", help="Enable or disable the optional options-backtest server for this and later starts; omitted keeps the saved choice.")` and forward it. `stop`, `teardown`, `upgrade`, `update` are unchanged. `status` (`:670-682`) appends `("Options Backtest", config.mcp_options_backtest_url)` only when `config.enable_options_strategy` is true; the JSON shape is otherwise unchanged, so a default install's `all_healthy` no longer depends on a server it never started, and the gate's preflight (`preflight.py:250`) passes on default machines. `config show` (`:1109-1126`) prints, after the hub settings, a new section headed `OBaI Optional Components (~/.obai/.env):` with one row, `options backtest  enabled|disabled  (from ~/.obai/.env | env ENABLE_OPTIONS_STRATEGY | default)`, computed from `_ENV_FILE` (`:855`) and `_env_override("ENABLE_OPTIONS_STRATEGY")`; when the environment holds the key and differs from the file it prints the same red "outranks the file" note the hub rows use, and the row ends with `enable with: obai start --with-options-backtest` when disabled. No new `config` subcommand.

The skill directory is static (`HUB_SKILLS_DIR`, `:87`, `:1414-1415`) and stays loadable in both states; `test_central_hub_builders.py:37`'s count of 7 is unchanged. Whether to hide the skill when disabled is not pursued: the skill is what makes the hub refuse to proxy an options strategy through `strategy_analysis` (ADR 0003 §3), which matters more, not less, when the route is absent.

## 8. E2E gate (`.claude/skills/obai-e2e-regression`)

**Problem.** With the default off and `obai status` no longer listing the server, preflight passes on a default machine and the four `CORE-OPTSTRAT-*` cases (`cases.yaml:838-969`, 26 of core's exactly-enforced 220 calls, 4 of 26 cases) would run paid and fail routing. The bound is the computed task's two halves: the default release gate must not fail merely because an optional component is absent, and must not silently pass without it.

**Options weighed.** (a) Keep them in core and have preflight fail unless the opt-in is on: fails the first half on every machine without the component. (b) `disabled: true` or a new tier: `disabled` cases leave lint's exact budgets (`lint_cases.py:895,1026,1102`) but not `test_skill_doc_tier_table_matches_the_case_file` (`test_lint_cases.py:399` filters on `tier` only), so the two checks disagree; a new tier needs `TIERS`, budget keys and a `SKILL.md` row, and either way the cases stop running on machines that *have* the component, which is the opposite of what an optional component wants. (c) A per-case required capability that the runner resolves from the same effective environment as `obai status`: cases stay in core, run wherever the component exists, and are reported — not run, not passed — where it does not. **Decision: (c).**

**Case file.** Each `CORE-OPTSTRAT-*` case gains `requires: [options_backtest]`. Budgets (`cases.yaml:42-43`) and the `SKILL.md` tier row stay `26 | 220`: the static contract is the full gate. `lint_cases.py` gains `OPTIONAL_CAPABILITY_ENV: dict[str, str] = {"options_backtest": "ENABLE_OPTIONS_STRATEGY"}` (lint owns the case vocabulary; it and `preflight.py` are both leaf modules, and `run_suite.py` already imports from each) and one rule: `requires`, when present, is a non-empty list of distinct keys of that mapping, else `error invalid-requires`. Without the rule a misspelt key would be silently ignored, and today lint has no per-case key allowlist.

## 12. Risks

- **Pull fallback amplification (opted in).** `setup.sh:430` treats any single pull failure as total and rebuilds every image locally. If GHCR lacks `options-backtest-server:<version>` (the only registry probe, a dry-run pull, got a 401 from the token endpoint; unverified), an opted-in install builds all eleven images. Pre-existing shape; the fix (per-service pull or `--ignore-pull-failures`) is a separate change. Default installs are unaffected.
- **First upgrade onto the profile.** A source checkout that ran this branch's earlier compose file has a running container started by default-on code. `obai upgrade` runs the new `setup.sh`, whose opted-out removal finds and removes it; `obai stop` on the *old* checkout (pre-profile teardown) would not. A web UI started by the old code keeps its route to the removed container until `obai restart`, because `obai upgrade` and `setup.sh` never relaunch a running web UI; the summary says so because the run removed a container. That relaunch gap predates this change (`_confirm_upgrade`'s "restarts the services and web UI" is already inaccurate at HEAD) and changing `_apply_upgrade` to tear down first is the owner's call. Documented in the CHANGELOG entry.
- **Shell exports.** `ENABLE_OPTIONS_STRATEGY` exported in a shell still outranks the file for the CLI and hub (§1). Made visible (`config show`, gate fingerprint), not eliminated.
- **`OBAI_HOME`.** `setup.sh`/`install.sh` honour it; `chat.py:855,1131`, `lifecycle.py:37` and `preflight.py:47` hard-code `~/.obai`. With a custom `OBAI_HOME` the opt-in lands where the CLI never looks. Pre-existing for every key in the file; noted, not fixed. Its new consequence: a later `obai start` from a shell without that `OBAI_HOME` reads `~/.obai/.env`, finds no opt-in and removes the container (the summary reports the removal). Recorded in the CHANGELOG entry.
- **Partial gate as release gate.** A green core run with four `skipped_not_applicable` cases proves nothing about the options route; §15 Q1.
- **Default state ungated.** Every default install now meets the absent-route path for options-structure requests, and no gate case exercises it: the four cases need the opt-in, and the runner has no inverse condition. What the hub says there — refusing to proxy through `strategy_analysis`/`options_analysis` or answer from training data — is pinned only by unit tests of the prompt and skill text; §15 Q3.
- **Compose version.** `--profile` and `profiles:` exist on every Compose v2 release; no minimum-version check is added. `--profile '*'` is avoided for that reason.
- **Help-text drift.** Replaced the fixed `head|tail` window with a range; a test pins that every parsed flag appears in `--help`.

## 15. Owner questions (product policy), each with the default that applies unless answered

1. **Does a core gate run with the four `CORE-OPTSTRAT-*` cases `skipped_not_applicable` count as the release gate?** Recommended default: not for a release whose diff touches `src/options-backtest-server/`, `core_agents/options_strategy_agent.py`, `prompts/options_strategy.md`, the routing skill, or those four cases; for such releases the gate must run with the opt-in on and `skipped: []`, and the gate `SKILL.md` states this. 2. **Should `install.sh` ask about the component when stdin is a terminal (the two-step download path)?** Recommended default: no. One flag, documented in the README and printed in the post-install banner, keeps the piped and downloaded paths identical and keeps the installer free of a decision most first-time users cannot yet make (the component validates strategies and reports historical backtesting as unavailable, ADR 0003 §1.7).
3. **Should the gate cover the default state, where `options_strategy_analysis` is absent?** Recommended default: not now. A core case that runs only when the opt-in is off needs an inverse condition (`requires_absent`) in lint and the runner, and changes core's exactly-enforced budgets (`26 | 220`); until the owner asks for it, the absent-route answer is pinned by the unit tests of the skill and base-prompt text (§12).
